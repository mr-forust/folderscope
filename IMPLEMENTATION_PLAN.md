# План исправлений по результатам аудита FolderScope

Дата аудита: 2026-10-09

## Executive Summary

FolderScope — локальное настольное приложение на C++20 и Qt 6 для поиска файлов без индекса и фоновой службы. В целом проект компилируется, а имеющиеся тесты проходят. Обнаружены дефекты поиска содержимого и ограничения результатов, неполная обработка ошибок чтения, риск выполнения PR-кода на self-hosted runner, пробел в Arch build dependencies и слабые проверки при публикации релизов.

Подтверждённые проблемы и риски:

| Приоритет | Количество | Основной ущерб |
| --- | ---: | --- |
| P0 — Critical | 0 | Критических подтверждённых уязвимостей или потери данных не обнаружено |
| P1 — High | 2 | Неустановленная изоляция self-hosted runner; фактический runner не имеет CMake и не может выполнять CI |
| P2 — Medium | 10 | Неполные/неверные результаты, ошибки релизов, сборки и экспорта, замедление поиска |
| P3 — Low | 5 | Ошибки крайних случаев и неполнота метаданных |

Аудит охватил 38 отслеживаемых файлов и 3 неигнорируемых новых файла рабочей копии. Существующие изменения пользователя включены в проверку и не изменялись. Игнорируемые артефакты сборки и упаковки не рассматривались как исходный код.

Автоматический Codex Security Deep Scan не запустился: сервер потребовал управляемый профиль разрешений файловой системы, а для задачи был доступен профиль без такого управления. Поэтому security findings ниже получены ручным анализом исходников и конфигураций; это ограничение покрытия, а не результат «уязвимостей нет». На момент первоначального аудита конфигурация runner, фактические разрешения Gitea, опубликованные workflow runs, чистая Arch-среда и внешние CVE-базы не были доступны. Последующие проверки сборки и текущий статус runner зафиксированы в разделе результатов реализации.

## Architecture Overview

### Компоненты и потоки данных

1. main.cpp создаёт QApplication, загружает перевод и переносит прежние настройки в новое пространство QSettings.
2. MainWindow владеет поисковыми настройками, таблицей результатов, экспортом и действиями с выбранными путями.
3. OptionsDialog редактирует корневые каталоги, маски, фильтры, режимы, профили и историю ввода.
4. SearchEngine выполняет обход каталогов в рабочем QThread, отбирает кандидатов, ищет содержимое и вычисляет группы дубликатов.
5. search_core.cpp содержит сопоставление масок, проверку файловых метаданных, чтение содержимого, хеширование и сравнение файлов.
6. SearchCache сериализует результаты хеширования и поиска содержимого в файл по пути Qt CacheLocation. QSettings хранит параметры интерфейса, профили и историю путей/фильтров.
7. ResultsModel и QSortFilterProxyModel представляют и сортируют результаты; MainWindow открывает, перемещает, удаляет, переименовывает и экспортирует файлы.
8. Gitea Actions собирает приложение на self-hosted runner. Релиз публикует архив и Arch-пакет в Gitea; Linux-релиз использует GITEA_TOKEN для API.

Сервера приложения, удалённой базы данных и сетевого протокола поиска нет. Основные границы доверия — содержимое и имена файлов, введённые пользователем пути, локальные настройки/кэш, PR-код, runner и release token.

### Проверенный состав

- Приложение: src/main.cpp, src/main_window.*, src/options_dialog.*, src/search_engine.*, src/search_core.*, src/search_cache.*, src/results_model.*, src/long_long_spin_box.*, src/tabular_text.*.
- Сборка и доставка: CMakeLists.txt, .gitea/workflows/ci-release.yaml, scripts/release.sh, packaging/*, README.md, CHANGELOG.md, VERSION.
- Тесты: tests/*; русский перевод: translations/folderscope_ru.ts.

## Audit Findings

### P1 — High

- **AUD-01.** PR-код выполняется на self-hosted runner, а из репозитория нельзя подтвердить изоляцию заданий и границы доступа к runner.
- **AUD-17.** Фактический VPS runner работает на Ubuntu без CMake; все main/tag verify jobs завершаются до сборки и блокируют публикацию.

### P2 — Medium

- **AUD-02.** Релиз проверяет совпадение номера версии, но не доказывает, что собирается и публикуется commit указанного тега или доверенной ветки.
- **AUD-03.** Workflow использует изменяемые ссылки на внешние действия/образы; release token доступен всему Linux publish job.
- **AUD-04.** maxResults ограничивает кандидатов до классификации дубликатов и не соответствует результатам режима.
- **AUD-05.** Включение поиска папок полностью выключает фильтр содержимого.
- **AUD-06.** Ошибки доступа/чтения не отражаются в полноте поиска; файлы с неудачным хешированием попадают в результаты «не-дубликаты».
- **AUD-07.** Регистр при поиске содержимого сравнивается побайтно, поэтому Unicode-буквы не получают ожидаемого нечувствительного к регистру сравнения.
- **AUD-08.** Arch PKGBUILD не объявляет qt6-tools, хотя CMake требует Qt6 LinguistTools.
- **AUD-09.** Маски компилируются в регулярные выражения при обработке каждого элемента дерева.
- **AUD-10.** Экспорт сообщает об успехе, даже если запись или сброс буфера завершились ошибкой.
- **AUD-11.** При повторной публикации workflow удаляет существующий asset до подтверждённой загрузки замены.

### P3 — Low

- **AUD-12.** Действие «Open With…» открывает файл приложением по умолчанию и не даёт выбрать приложение.
- **AUD-13.** Пустой после удаления пробелов hex-запрос становится пустой иглой и совпадает со всеми файлами.
- **AUD-14.** Исключённая папка всё равно возвращается как результат, если включён поиск папок.
- **AUD-15.** XML-экспорт не удаляет символы, запрещённые XML 1.0, из имён и путей.
- **AUD-16.** AppStream-метаданные не содержат homepage URL; локальный валидатор завершился с предупреждением и ненулевым кодом.

## Implementation Roadmap

### Этап 1 — Граница доверия CI и происхождение релиза

1. AUD-01: установить фактическую модель runner и убрать выполнение недоверенного PR-кода с неограниченного self-hosted окружения.
2. AUD-03: закрепить версии внешних действий и образов; сузить разрешения токена и время/область его выдачи.
3. AUD-17: согласовать воспроизводимую среду сборки с фактическим runner и его свободным местом.
4. AUD-02: привязать релиз к commit тега и доверенной ветке; проверить и workflow_dispatch, и локальный release script.
5. AUD-11: обновлять assets без удаления последней рабочей копии до успешной загрузки замены.

### Этап 2 — Корректность результатов поиска

1. AUD-05: исправить взаимодействие content search и findFolders.
2. AUD-04: определить лимит как лимит итоговых результатов и применить его после фильтрации/классификации.
3. AUD-06: сделать неполный обход и невозможность прочитать файл видимыми состояниями, исключить неизвестные файлы из «не-дубликатов».
4. AUD-07: перейти к Unicode-aware сопоставлению для текстовых запросов.
5. AUD-13 и AUD-14: закрыть подтверждённые крайние случаи запросов и исключений.

### Этап 3 — Надёжность сборки, экспорта и производительность

1. AUD-08: объявить LinguistTools build dependency и добавить проверку упаковки в чистой Arch-среде.
2. AUD-09: компилировать маски один раз на запуск поиска и сравнить производительность на большом дереве.
3. AUD-10 и AUD-15: атомарно писать экспорт, сообщать об ошибках и выдавать корректный XML для произвольных имён Linux-файлов.
4. AUD-12 и AUD-16: исправить действие Open With и AppStream-метаданные.

Задачи в одном этапе независимы, кроме случаев, явно указанных в карточках. В частности, задачи AUD-01, AUD-02, AUD-03 и AUD-11 меняют один workflow и должны быть реализованы согласованно, чтобы не перетирать правки друг друга.

## Detailed Tasks

### AUD-01 — Изолировать PR-задания на self-hosted runner

- **Приоритет:** P1 — High.
- **Затронутые компоненты:** .gitea/workflows/ci-release.yaml; конфигурация и область регистрации Gitea runner (вне репозитория).
- **Проблема и первопричина:** событие pull_request запускает verify job на labels self-hosted, linux, arch, homelab. Задание проверяет содержимое PR. В workflow нет собственного ограничения контейнера, ephemeral VM или границ доступа к runner. Режим выполнения определяется конфигурацией runner, которой в репозитории нет.
- **Доказательства:** ci-release.yaml:9,17-26. Документация Gitea описывает режимы host/container, рекомендует изоляцию и отдельно рассматривает одобрение fork PR: [Gitea Actions FAQ](https://docs.gitea.com/usage/actions/faq/), [Gitea Runner](https://docs.gitea.com/runner/). Workflow также объявляет write permissions на уровне всего файла, см. AUD-03.
- **Шаги исправления:** 1) проверить конфигурацию и регистрацию runner, доступные volumes, Docker socket, локальные credentials, рабочие каталоги и ограничения fork PR; 2) выполнять PR-проверки только в одноразовом контейнере/VM с минимальным read-only token и без секретов; 3) если изолированный runner недоступен, не запускать fork PR; в текущем workflow PR-trigger отсутствует, а ручная проверка ограничена `main`; 4) оставить публикацию только на тегах, commit которых проверен как достижимый из `main`.
- **Зависимости:** внешняя проверка runner должна предшествовать выбору окончательной изоляции; AUD-03 уменьшает доступные job permissions.
- **Критерии приёмки:** workflow не запускает код fork PR на self-hosted labels; `workflow_dispatch` с ref кроме `main` пропускает verify; обычный push main и проверенный tag остаются рабочими. Если PR-trigger будет возвращён, до этого подтвердить изоляцию runner или server-side approval.
- **Проверка:** проверить, что во всех `.gitea/workflows` нет PR-trigger; проверить условие ручного запуска и ancestry guard; выполнить workflow lint. Runtime режим runner и fork approval оставить непроверенными, если административный доступ отсутствует.
- **Статус:** DONE — `pull_request` не включён ни в один workflow; ручная проверка выполняется только при dispatch из `main`, а tag build проверяет, что commit достижим из `origin/main`. В тестовых run logs подтверждён host executor на VPS (`vps` v3.0.2; labels включают `prod`), поэтому доверенные jobs не изолированы от хоста. Fork PR не запускается; approval policy остаётся непроверенной.

### AUD-02 — Привязать публикуемый артефакт к commit релизного тега

- **Приоритет:** P2 — Medium.
- **Затронутые файлы:** .gitea/workflows/ci-release.yaml, scripts/release.sh, tests/release_dirty_test.sh.
- **Проблема и первопричина:** проверяется только равенство VERSION и строки версии. В Arch publish job архивируется HEAD, а workflow_dispatch принимает release_tag, но не сверяет HEAD с commit этого тега. Локальный скрипт ставит тег на текущий HEAD и не проверяет, что это main или commit, достижимый из main. Оператор может запустить публикацию с другой ветки, где совпадает VERSION.
- **Доказательства:** ci-release.yaml:28-33,154-175; script выпускает текущий HEAD в scripts/release.sh:25-34. Gitea задаёт event ref для workflow_dispatch; см. [Gitea Actions variables](https://docs.gitea.com/usage/actions/actions-variables/).
- **Шаги исправления:** 1) для ручной публикации разрешать только существующий тег ожидаемого формата; 2) разрешить тег в peeled commit и проверить, что checkout/архив соответствует этому commit; 3) для release tag проверить принадлежность commit защищённой main-ветке; 4) в scripts/release.sh отказывать на неподдерживаемой ветке и при отсутствии требуемого ancestry; 5) сохранять SHA исходного commit в release metadata или сводке job.
- **Зависимости:** выполнять после согласования безопасных триггеров в AUD-01 и минимальных permissions в AUD-03.
- **Критерии приёмки:** ветка с совпадающим VERSION, но другим commit, не может опубликовать Arch-пакет; ручной ввод тега не позволяет архивировать иной HEAD; тег из main проходит все gates.
- **Проверка:** добавить тестовые случаи для tag commit, неподходящей ветки, несовпадающего HEAD и чистой main-ветки; проверить workflow на тестовом теге без загрузки реального пакета.
- **Статус:** DONE — workflow проверяет commit тега и его достижимость из origin/main; release script требует чистую синхронную main; release-guards-main-ref прошёл в CTest.

### AUD-03 — Закрепить CI-зависимости и сузить права job token

- **Приоритет:** P2 — Medium.
- **Затронутый файл:** .gitea/workflows/ci-release.yaml.
- **Проблема и первопричина:** workflow-level permissions задаёт contents: write и packages: write всем jobs; verify запускается также для pull_request. actions/checkout@v4 и образ cytopia/yamllint:latest являются изменяемыми ссылками. В Linux publish job GITEA_TOKEN находится в job-level env и доступен всем его шагам, включая внешний checkout action.
- **Доказательства:** ci-release.yaml:17-26, 58-60 и 101-152. Документация Gitea указывает, что workflow permissions определяют права GITEA_TOKEN; fork PR имеет отдельное read-only ограничение, но оно не заменяет least-privilege для всех job: [Gitea token permissions](https://docs.gitea.com/usage/actions/token-permissions/).
- **Шаги исправления:** 1) переопределить verify permissions как read-only; 2) оставить write scope только публикационным job и только необходимые scope; 3) передавать `GITEA_TOKEN` на уровне команд/шагов API, не checkout/build; 4) закрепить actions по полному commit SHA и контейнерный образ по digest либо использовать поддерживаемую внутреннюю копию; 5) документировать процесс обновления закреплённых версий; 6) для Arch package не полагаться на `GITEA_TOKEN`: на Gitea 28 попытки с `packages: write` вернули 401 и для Arch, и для Generic registry. После согласования хранить отдельный PAT только со scope `write:package` в Actions secret и передавать его только шагу загрузки; проверить в отдельной тестовой группе. Не выдавать этот PAT шагам checkout/build.
- **Зависимости:** координировать с AUD-01 и AUD-02, так как они меняют тот же workflow.
- **Критерии приёмки:** verify не имеет write token; ни один внешний build/test action не получает release/package token; версии действий и образов разрешаются в неизменяемые идентификаторы; release job создаёт release и загружает assets; Arch job загружает пакет в отдельную тестовую группу через токен только со scope `write:package`.
- **Проверка:** проверить рассчитанные права Gitea job token для main push и tag; выполнить release API test на тестовом репозитории; проверить Arch/Generic registry на test job token; выполнить пакетную запись отдельным scoped PAT после его безопасного provision; убедиться, что workflow lint проходит.
- **Статус:** PARTIAL по решению пользователя. PAT `folderscope-package-publish-20261009` имеет ровно scope `write:package`; secret `FOLDERSCOPE_PACKAGE_TOKEN` настроен в `folderscope` и `test-folderscope`, значения не читались и не выводились. Test run 1764 загрузил synthetic Arch package (HTTP 201); прежний тестовый PAT отозван. Основной workflow Arch job запрашивает только `code: read` и передаёт PAT только шагу загрузки, однако изменения workflow остаются локальными и не опубликованы. Полный запуск main workflow не проверен из-за AUD-17; пользователь явно оставил AUD-03 частичным. Предыдущие runs 1758/1760 подтверждают HTTP 401 для built-in `GITEA_TOKEN` с `packages: write` в Arch/Generic; run 1756 успешно создал release и загрузил два synthetic assets. Fork job ограничен read-only. Screenshot `test-folderscope` показывает включённые Actions, owner override и default `Permissive`; `Packages` отсутствует среди maximum-permission units. Actions/yamllint закреплены; create/upload helpers покрыты HTTP mock tests.

### AUD-04 — Применять maxResults к итоговым строкам, а не к кандидатам

- **Приоритет:** P2 — Medium.
- **Затронутый файл:** src/search_engine.cpp; тесты tests/search_engine_test.cpp; подпись параметра в src/options_dialog.cpp.
- **Проблема и первопричина:** при пустом contains обход прекращается, как только набрано maxResults кандидатов (строки 197-198), до группировки дубликатов, duplicate-name анализа и отбора «не-дубликатов». В итоге лимит кандидатов может вернуть ноль строк, хотя подходящие совпадения находятся дальше. При content query фильтр сначала полностью обходит кандидатов, затем обрезает список; надпись «Stop after finding» обещает остановку раньше.
- **Доказательства:** src/search_engine.cpp:197-198,249-268,277-408. Одноразовый воспроизводимый сценарий: два одинаковых файла, режим Duplicates search, maxResults=1 и showDuplicateCopiesOnly=false дают 0 строк.
- **Шаги исправления:** 1) определить maxResults как ограничение итоговых строк после всех активных фильтров и классификаторов; 2) не прекращать сбор кандидатов до того, как режим может определить принадлежность к итогам; 3) где безопасно, остановить content scan после N подтверждённых итогов, а где семантика требует полного прохода, переименовать подсказку в «Ограничить число результатов»; 4) добавить точечные метрики, если лимит не может прекратить обход.
- **Зависимости:** согласовать с AUD-05, чтобы content predicate применялся до подсчёта итогов.
- **Критерии приёмки:** для всех режимов maxResults ограничивает число строк после классификации; лимит не скрывает дубликаты только из-за порядка обхода; поведение контентного поиска соответствует тексту интерфейса.
- **Проверка:** тесты с лимитом 1 для пары одинаковых файлов, пары файлов с одинаковым именем, режима Non-Duplicates и content search; проверить, что число итогов не превышает лимит и подходящие группы не пропущены.
- **Статус:** DONE — лимит применяется к итоговым результатам; CTest покрывает duplicate, non-duplicate, duplicate-name и несколько корней.

### AUD-05 — Не отключать content search при включённом поиске папок

- **Приоритет:** P2 — Medium.
- **Затронутый файл:** src/search_engine.cpp; тесты tests/search_engine_test.cpp.
- **Проблема и первопричина:** условие на строке 249 запускает контентную фильтрацию только при !findFolders. При включении Find folders фильтрация не выполняется ни для файлов, ни для папок, и несоответствующие файлы попадают в результаты.
- **Доказательства:** src/search_engine.cpp:249-268. Временный тестовый каталог с файлом «unrelated», contains=«needle», findFolders=true и findFiles=true вернул «unrelated».

- **Зависимости:** AUD-04.

## Verification Strategy

Для реализации задач использовать небольшие regression tests, не полагаясь на успешную сборку как на доказательство корректности.

### Поиск и файловые операции

- Проверить комбинации findFiles/findFolders, content query, каждый search mode и maxResults.
- Проверить порядок обхода и результаты при нескольких совпадениях после первых кандидатов.
- Проверить Unicode case pairs, binary query validation и границы 1 MiB content chunks.
- Проверить доступные/недоступные файлы и каталоги, ошибки чтения, частичный traversal, отмену и видимый incomplete status.
- Убедиться, что Non-Duplicates никогда не включает объекты с неизвестным результатом сравнения.
- Проверить recursive/non-recursive исключения папок.
- Проверить сохранность существующего экспортного файла при искусственной ошибке записи; затем разобрать все форматы независимыми парсерами.
- Повторно проверить безопасное открытие регулярных файлов, отказ от FIFO и удаление directory symlink без удаления target.

### Сборка и упаковка

- Настроить Debug и Release сборку, выполнить полный CTest.
- Собрать Arch package в чистой Arch среде по объявленным PKGBUILD dependencies.
- Убедиться, что install tree содержит приложение, desktop entry, иконку, man page, AppStream metadata и перевод.
- Выполнить yamllint, bash -n, desktop-file-validate, xmllint и appstreamcli validate.
- Запустить tag и workflow_dispatch на тестовом Gitea repository: неверный ref/commit должен отказать до публикации; ошибка upload должна сохранить старые assets.

### Безопасность CI

- Проверить эффективные Gitea token permissions отдельно для PR, main push и release.
- Проверить runner execution mode, mounts, ephemeral lifecycle, Docker socket и approval policy для fork PR.
- Убедиться, что verify job не получает write token и release token не попадает в build, checkout, lint или test steps.
- Проверить, что внешние actions и container images закреплены на неизменяемых commit/digest.

## Risks & Compatibility

- Изменение maxResults может увеличить объём обхода для duplicate modes: необходимо сохранить корректную классификацию до ограничения итогов. Не ухудшать смысл существующей пользовательской настройки без уточнения её текста.
- Content search должен продолжать читать большие файлы потоково и учитывать cancellation. Unicode-aware сравнение не должно загружать целые файлы в память.
- Нельзя помечать unreadable файлы как unique. Добавление incomplete status меняет текст завершения поиска и должно быть понятно локализовано.
- Внедрение QSaveFile сохраняет прежний экспорт до завершения нового, но при записи на сетевые/несовместимые файловые системы возможны особенности commit/rename; проверять ошибку и показывать её.
- Runner workflow и выпуск пакетов требуют согласованного изменения нескольких участков. Не менять production runner или Gitea secrets в рамках реализации кода без отдельной инфраструктурной процедуры.
- Pinning actions уменьшит автоматическое получение обновлений; обновления потребуют периодического контролируемого пересмотра.
- XML не способен представить все возможные байтовые имена POSIX без преобразования. Нужно документировать отображение недопустимых символов; CSV/JSON должны сохранять свою отдельную семантику.

## Definition of Done

- Для каждой задачи с выбранным scope все критерии приёмки проверены, статус обновлён с TODO на DONE только после наличия доказательств.
- Regression tests воспроизводят исходный дефект и проходят после исправления.
- Полные CMake build и CTest проходят; дополнительно проходят относящиеся к изменению package/workflow validators.
- Trusted main/tag Actions проходят на фактически выбранном runner; live release API и package registry проверены в изолированных тестовых namespace.
- CI не запускает fork PR и ручную проверку произвольной ветки на self-hosted runner; если PR workflow будет возвращён, сначала проверить изоляцию runner и approval policy.
- Каждый release archive/package привязан к ожидаемому commit и тегу, а сбой публикации не удаляет последнюю рабочую копию assets.
- Поиск сообщает неполное покрытие и не классифицирует непрочитанные файлы как уникальные.
- Экспорт не сообщает об успехе при ошибке записи, не повреждает предыдущий файл и выдаёт корректные форматы.
- Изменения не затрагивают пользовательские данные, локальные настройки, кэш или production-инфраструктуру вне утверждённой процедуры.
